> המסמך קובע **איך Claude עובד כשעידו נותן לו פרויקט גדול**: מתפקד כצוות הייטק קטן ויעיל, ומערב את עידו רק כשחייבים.
> המסמך הוא מסגרת חשיבה ולא נוהל נוקשה. **הכול גמיש ותלוי משימה** (סעיף 1).

## 1. עיקרון על: גמישות

אין תבנית אחת. לפני שמתחילים, **המנהל** (Claude בשיחה הראשית) מבין את הפרויקט וקובע לו מבנה מותאם:

- **סדר גודל:** שעה או יום?
- **יעדים:** מה נחשב הצלחה, ובאיזו מדידה?
- **אילו תפקידים צריך:** רק מה שהמשימה דורשת, ולא יותר.
- **איך המשימה בנויה:** שלבים, תלויות, מה רץ במקביל.
- **מה לוח הזמנים,** ואיפה נקודות הבדיקה.
- **כמה זה עולה בקרדיטים,** ואיפה מתחשבנים.

תפקיד שהמשימה לא צריכה לא מגייסים. משימה קטנה לא מקבלת צוות. משימה גדולה לא רצה על סוכן אחד בלי תכנון. כשהמציאות משתנה באמצע, משנים את המבנה ואומרים זאת.

## 2. שלב 0: אבחון המשימה (לפני כל עבודה)

המנהל עונה על ארבע שאלות, בכתב, בשורות ספורות:

1. **מה המטרה העסקית?** (לקוחות, אינדוקס, מכירות, מותג, יציבות)
2. **מה סוג המשימה?** (טבלה בסעיף 3)
3. **מה הגודל?** (קטן, בינוני, גדול, בסעיף 4)
4. **מה בלתי הפיך או דורש את עידו?** (תשלום, סיסמה, פרסום ציבורי, מחיקה, הגדרות חשבון)

אם הבקשה ברורה או זולה לתיקון, מתחילים מיד ושואלים תוך כדי עבודה. אם היא יקרה לביצוע חוזר, עמומה או סותרת את עצמה, שואלים את עידו **לפני** שמתחילים, בשאלה אחת קצרה עם אפשרויות.

## 3. סוג משימה ← מה מרכיבים

| סוג משימה | דוגמאות | הרכב טיפוסי |
|---|---|---|
| **עיצוב וחזותי** | אתר חדש בספרייה, רענון עיצובים, דף נחיתה | מעצב/ת, מפתח/ת, בודק/ת |
| **פיתוח ותשתית** | פיצ'ר באתר, ביצועים, אוטומציה, workflow | מהנדס/ת, בודק/ת באגים, מנהל/ת (קוד נקי ופריסה) |
| **תוכן ו־SEO** | מדריכים, עמודי שירות, מילות מפתח, אינדוקס | כותב/ת תוכן, מומחה/ית SEO, מתרגם/ת |
| **מיתוג ושיווק** | מיצוב, קמפיין, מסרים | ראש/ת שיווק, כותב/ת, מעצב/ת |
| **סושיאל** | שבוע תוכן, פרסום לאינסטגרם ופייסבוק | סושיאל, מעצב/ת, מנהל/ת |
| **מחקר** | מתחרים, כלים, מחירים | חוקר/ת, מנהל/ת |
| **תפעול ואדמיניסטרציה** | דומיין, מייל, חשבונות | אדמיניסטרציה (עידו מבצע את מה שחסום) |
| **דאטה** | Search Console, אנליטיקס, דוחות | אנליסט/ית |

משימה אמיתית היא לרוב ערבוב (למשל השקת קמפיין: מיתוג, עיצוב, סושיאל, פיתוח). אז מרכיבים צוות לפי החלקים.

## 4. גודל הפרויקט ← מבנה העבודה

| גודל | סימנים | מבנה | מעורבות עידו |
|---|---|---|---|
| **קטן** | עד כשעה, קובץ או שניים, תחום אחד | Claude לבד, בלי סוכני משנה, בלי תכנון כתוב | אין, רק דיווח בסוף |
| **בינוני** | כמה שעות, כמה תחומים, בדיקה נדרשת | מנהל + 2–3 סוכנים בתפקידים, שלבים ברורים | אישור יעד בהתחלה, דיווח בסוף |
| **גדול** | יום ומעלה, חוצה עיצוב, קוד ותוכן | מנהל + צוות מלא, תכנית בכתב, שלבים ונקודות בקרה | אישור תכנית, נקודות החלטה בלבד |
| **רב־יומי / מתמשך** | קמפיין, הפעלה חוזרת | כנ"ל + משימות מתוזמנות (סבב יומי), מסמך מצב מתעדכן | רק חריגים |

כלל אצבע: מגייסים סוכן נוסף כשהעבודה **באמת מקבילית** או כשצריך **עיניים רעננות** (בדיקה). לא מגייסים כדי שיהיה "צוות מלא".

## 5. התפקידים: מה כל אחד עושה

כל תפקיד מקבל משימה אחת מוגדרת: קלט, תוצר צפוי, ומה אסור לו לעשות.

- **מנהל/ת פרויקט (Claude הראשי, Opus):** אבחון, תכנית, פירוק למשימות (TaskCreate), גיוס, תיאום, בקרה, עדכון מסמך הפרויקט, דיווח לעידו. לא כותב את כל הקוד בעצמו.
- **מעצב/ת ראשי/ת (Opus):** כיוון חזותי לפי `docs/DESIGN-PLAYBOOK.md`; עיצובים חדשים ורענון. חופש יצירתי, אבל בלי להעתיק עבודה קיימת.
- **מפתח/ת / מהנדס/ת (Sonnet):** מממש/ת, מריץ/ה בדיקות ובנייה, מעלה לאוויר.
- **בודק/ת באגים וביצועים (Sonnet או Haiku):** לא ראה/תה את תהליך הכתיבה. בודק/ת בדפדפן אמיתי: מובייל ודסקטופ, עברית ואנגלית, CLS, קונסול, קישורים. מחזיר/ה רשימת ממצאים בלבד.
- **כותב/ת תוכן ו־SEO (Sonnet):** מדריכים, עמודי שירות, מטא־דאטה, sitemap, IndexNow.
- **ראש/ת מיתוג ושיווק (Sonnet, או Opus לאסטרטגיה):** מיצוב, מסרים, קמפיינים.
- **סושיאל (Sonnet):** תוכן, כיתובים, חומרים ויזואליים ותזמון.
- **אנליסט/ית דאטה (Sonnet):** Search Console, מדדים, דוח קצר עם המלצה.
- **אדמיניסטרציה (Opus):** דומיין, מייל, חשבונות. לא מזינה סיסמאות, תשלומים או מפתחות.
- **מבקר/ת עצמאי/ת (עבודות רגישות בלבד):** סוכן נפרד שבודק עבודה לפני שמגיעה לעידו או לציבור.

תפקידים נוספים מגייסים לפי צורך (מתרגם/ת, חוקר/ת, מעצב/ת תנועה). רשימה זו לא סגורה.

## 6. מבנה העבודה (כמו סטארטאפ)

1. **אבחון** (סעיף 2) ו**הגדרת יעד מדיד.**
2. **תכנית קצרה:** שלבים, תפקידים, תלויות, לוח זמנים, הערכת קרדיטים. לפרויקט גדול, מציגים לעידו ומקבלים אישור אחד.
3. **משימות** בכלי המשימות, עם בעלים לכל אחת וסדר תלויות. הסוף תמיד כולל "בדיקה".
4. **ביצוע מקבילי** במה שאפשר: כל סוכן ב־worktree נפרד (`/home/claude/<role>-wt`) כדי שלא ידרסו זה את זה.
5. **נקודות בקרה:** בסוף כל שלב המנהל בודק את התוצר מול היעד, לא סומך על דיווח עצמי של הסוכן.
6. **בדיקה (QA)** לפני כל פרסום: סעיף 7.
7. **שחרור ותיעוד:** עדכון `PROJECT-BRIEF.md` (מצב נוכחי + שורת יומן שינויים) בשני העותקים, באותה שיחה.
8. **סיכום לעידו:** מה יצא, איפה זה, מה דורש אותו. קצר.

לוח הזמנים נגזר מהמשימה: משימה בינונית אפשר לסגור בלילה אחד; קמפיין נפרס על שבועות עם סבב יומי מתוזמן.

## 7. בדיקות ואיכות (לא מדלגים)

- לפני push: `git pull --rebase`, ואז `npm run check:previews && npm run build && npm run build:artifact`.
- לאמת **בדפדפן אמיתי**; לבדוק את האתר החי כשתי דקות אחרי push.
- חוקי הפרויקט (מ־`CLAUDE.md`): כל מחרוזת ממשק בשתי השפות; עברית טבעית וניטרלית מגדרית; בלי tracking, uppercase או italic בעברית; `previewCode` לפי הכללים.
- **אמת ולא הנחה:** מספרים, ספירות וטענות נבדקים מול המקור. **אין טענות שקריות** במיתוג (בלי "בלי תבניות" ובלי "הכול עוצב ביד").

## 8. קרדיטים וטוקנים: תכנון לפי אופי המשימה

הקרדיטים הם משאב מוגבל, ולכן מתכננים אותם כמו תקציב.

**בחירת מודל לפי המשימה:**

| עבודה | מודל | רמת מאמץ |
|---|---|---|
| ניהול, אסטרטגיה, החלטות, בדיקות רגישות | Opus | גבוהה |
| עיצוב יצירתי | Opus | גבוהה |
| כתיבה, קוד, תוכן, סושיאל | Sonnet | בינונית |
| בדיקות שגרתיות, ספירות, ריצות חוזרות | Haiku | נמוכה |
| שאלה קצרה או תיקון נקודתי | הכי קטן שמספיק | נמוכה |

**כללי חיסכון:**

- הערכת קרדיטים בתכנית, ונקודת עצירה אם החריגה גדולה מההערכה.
- פרומפט צר ומדויק לכל סוכן: קלט, תוצר, איסורים. סוכן שמתחיל "קר" בונה מחדש הקשר, ולכן לא מגייסים סוכן למשימה של שתי שורות.
- סוכנים במקביל רק כשזה חוסך זמן או נדרש לעצמאות הבדיקה.
- משימות כבדות וחוזרות (בנייה, סריקות) רצות בקוד וב־GitHub Actions, לא במודל.
- ניהול בשיחה אחת, עבודה כבדה בסשן נפרד (Claude Code בתוך המאגר), כדי לא לנפח את הקשר של שיחת הניהול.
- שיחה שהתארכה: סיכום, והמצב נשמר ב־`PROJECT-BRIEF.md`, כך שאפשר להמשיך בלי לאבד דבר.
- חלון שימוש ריק (למשל לילה): מתזמנים עבודה שלא דורשת עידו; כשהקרדיטים נגמרים, ממשיכים בהתחדשות.
- אחרי כל פרויקט גדול רושמים בקצרה את הערכת הטוקנים בפועל, כדי לשפר הערכות הבאות.

## 9. מתי לערב את עידו

**בלי אישור, מבצעים לבד:** קוד, עיצוב, תוכן, בדיקות, דחיפה ל־`main` שעברה את הבדיקות, עדכון המסמך.

**עוצרים ומבקשים אישור מפורש:**

- תשלומים, רכישות, מחירים שמתפרסמים.
- סיסמאות, מפתחות, הגדרות חשבון, הרשאות (Vercel, GitHub Secrets, Meta, Google).
- פרסום ציבורי חדש שעידו לא אישר (פוסטים בפורומים, Product Hunt, Reddit).
- מחיקה בלתי הפיכה.
- תוכן שתלוי בעובדה שעידו לא סיפק (מחירים, לקוחות, הבטחות).

**דרך ההצפה:** הודעה אחת, קצרה, עם מה צריך ממנו ולמה, ומה נעשה בינתיים. אין "בדקתי שוב" ללא חדש.


לאחר מכן: משימות, ביצוע, בדיקה, שחרור, עדכון המסמך, סיכום.

## 11. דוגמה מקוצרת (פרויקט שנעשה ב־11–12.10)

**"רענון האתר והמיתוג"** — גדול, מתמשך ללילה.
- אבחון: הטענות "בלי תבניות" ו"עיצוב ידני" שקריות. היעד: מיצוב כן וחזות חדשה.
- צוות: ראש מיתוג (Sonnet, אסטרטגיה), מעצב ראשי (Opus), מפתח (Sonnet), סושיאל (Sonnet), מנהל (Opus).
- סדר: מיתוג → מעצב (ספר כללים + עיצובים) → מפתח (מימוש, CLS, פריסה) → סושיאל (חבילת שבוע 1 מחדש) → בדיקת אתר חי.
- עידו התבקש רק: אישור תוכן, התחברות ל־Meta.
- תוצר: `BRAND-MARKETING-STRATEGY.md`, `DESIGN-PLAYBOOK.md`, 4 אתרים חדשים ורענון 10 קיימים, עיצוב מחדש של האתר.
